# 仕組みと技術的な注意点

[English →](ARCHITECTURE-EN.md) / [README に戻る](../README.md)

> [!CAUTION]
> 本ツールは日常を彩るための遊び道具です。実務では使わないでください。以下は「どう作ってあるか」の解説であり、安全性の保証ではありません。

## コンテナ形式

```
[0, 512)     スーパーブロック: salt(16) | nonce(24) | 暗号化された使用量(32) | コメント領域 or 乱数
[512, size)  データ領域: [長さ(8) | age暗号文] を先頭から詰める。残りは乱数
```

- **固定サイズ・非スパース**: `init` 時に全領域を乱数で実書き込みする。`ls` も `du` も追記前後で変わらない。追記後はコンテナの更新日時も元に戻す
- **各ファイル = 1レコード**: 元ファイル名・サイズ・更新日時・パーミッション・MIMEタイプ・追加日時 (メタデータ) と本体をまとめて [age](https://age-encryption.org/) (X25519 + ChaCha20-Poly1305) で公開鍵暗号化
- **マスク層**: データ領域全体を「公開鍵 + コンテナ固有 salt」から HKDF で導出した鍵の XChaCha20 キーストリームで覆う。age のテキストヘッダ (`age-encryption.org/v1` 等) やレコード境界はコンテナ上に現れず、未使用の乱数領域と区別できない
- **書き込み位置**: スーパーブロックに XChaCha20-Poly1305 で封印して保持。平文ヘッダは無い。追記時に書き換えるのは先頭72バイトだけ
- **コメント**: `init --comment` のメモは、スーパーブロックの72バイト目以降に `"WOTCNOTE" | version(1) | 長さ(2) | CRC32(4) | 本文` として平文で埋め込む (最大425バイト)。鍵なしで読める。コメントの無いコンテナではこの領域は乱数のままなので、目印と CRC が偶然一致することは事実上なく「コメントなし」になる (以前のバージョンで作ったカプセルも同様)。以前のバージョン (v1.0.3 以前) で `add` するとこの領域が乱数で上書きされ、コメントが消える
- **コメントの変更・消去** (`vault comment add/edit/erase`): 書くたびにコメント領域 [72, 512) 全体を乱数で埋め直してから書くので、短く書き換えても前のコメントの残りは平文で残らない。消去後は一度もコメントを付けなかったコンテナと見分けがつかない。別のファイルを壊さないよう、公開鍵で管理情報が復号できること (= このカプセル本体であること) を確かめてから書き、排他ロックを掛ける。mtime は変えない
- **開封**: 秘密鍵から公開鍵を導出 → マスクを外し → 各レコードを age で復号 → 展開。ファイル名はディレクトリ成分を除去し (パストラバーサル対策)、同名は `name (1).ext` として展開
- **容量不足**: `add` は「容量不足」とだけ返す。途中まで書いたデータは管理情報を進めないので既存レコードは壊れない
- **同時実行**: `add` はコンテナに排他ロック (`flock`)、`open` は共有ロックを掛ける。複数の `add` が同時に走っても順番待ちになり、互いのデータを上書きしない
- **破損時の救出**: あるファイルの暗号文が壊れていても、長さ情報が読める限り次のファイルへ進み、無事なものは全部取り出す。長さ情報が壊れた場合はそれ以降が読めない。一部でも壊れていれば `--and-destroy-key` は破棄を行わない
- **誤操作の防止**: `add` にカプセル自身の管理ファイル (コンテナ・公開鍵・`.tlock`) を渡してもスキップする (`vault add *` 対策)。既にカプセルがある場所での `init` は上書きせずに止まる
- **破棄**: 乱数で3回上書き → 切り詰め → ランダム名にリネーム → 削除 (macOS に `shred` が無いため自前実装)。対象はコンテナ・開封に使った鍵ファイル・`<コンテナ>.tlock`
- 保存形式に OS 依存部分は無く (整数は big endian 固定)、macOS と Linux の間でコンテナをやり取りできる

## 鍵分割 (Shamir's Secret Sharing)

秘密鍵を「グラフの線の y 切片」に見立てる。2-of-3 なら、y 切片が秘密鍵になる直線をランダムに1本引き、その線の上の点を3つ配る。
点1個だけでは通る直線が無数にあって切片は一切分からないが、点が2個あれば直線が1本に決まり、切片 = 秘密鍵が求まる。
3-of-N なら直線の代わりに放物線 (点3個で決まる) を使う。鍵を切り刻むのではないので、**K 個未満の欠片からは鍵の情報が1ビットも得られない**。

- 実装: age 秘密鍵の生 32 バイトを [OpenBao の shamir](https://github.com/openbao/openbao/tree/main/sdk/helper/shamir) (GF(256) 上の Shamir 分割) で分割
- 欠片の表記: `version | K | N | 番号 | カプセル指紋 (公開鍵 SHA-256 先頭4バイト) | 分割ID (乱数4バイト) | 本体` を bech32 (HRP `wotc-share-`) にして大文字で表記。チェックサムで書き写し間違いを検出し、大文字・小文字どちらでも読める
- 指紋で別カプセルの欠片の混入を、分割IDで「同じ鍵を分割し直した以前の欠片」の混入を検出する (分割し直すと別の多項式になるので、以前の欠片とは組み合わせられない)
- `init` で分割した場合、完全な秘密鍵はディスクに一切書かない。分割直後に先頭K個・末尾K個で復元できることを検証してから書き出す
- 開封時には一瞬だけ、その端末のメモリ上で完全な秘密鍵が復元される
- `--and-destroy-key` で消えるのは開封に使った欠片ファイルだけ。残りの欠片はカプセル消滅後はただの無意味な文字列

## タイムロック (drand / tlock)

「指定日まで開かない」を、ローカルで日付をチェックする方式で作ることはできない。時計の変更・コードの改造・素の age で直接復号する、のどれでも破れる。
鍵が手元にある限りチェックは飾りなので、「日時までは復号鍵がこの世に存在しない」方式を使う。

[drand](https://drand.love/) は Cloudflare・大学・研究機関など世界の十数団体 (League of Entropy) が共同運営する公開乱数ビーコンで、3秒ごとに「その回の署名」を公開している。
秘密鍵を「20XX年XX月XX日の回の署名」でしか解けない形 ([tlock](https://github.com/drand/tlock)、BLS12-381 上の IBE) で暗号化しておく。
その署名は運営団体の過半数が協力してその時刻に初めて作られる値なので、日時前には復号鍵がどこにも存在しない。

- 構成は「タイムロック **または** 非常口」。タイムロック鍵 (`<コンテナ>.tlock`) とは別に、通常の秘密鍵 / 欠片が非常口として残る
- quicknet チェーンの公開鍵・genesis・周期を埋め込んであるため、ロックはオフラインで可能。開封時だけ drand の HTTP ミラー (api.drand.sh / api2 / api3 / drand.cloudflare.com) に順に問い合わせる
- ロック先は「指定時刻以降に公開される最初のラウンド」。開封可能日時の表示は、コメント行ではなく age ヘッダの `-> tlock <round> <chainhash>` から計算する
- 手元の時計で早すぎる場合はネットワークに問い合わせない。時計を進めてもこの判定を抜けるだけで、drand が未来ラウンドの署名を返さないので開かない
- 計算量タイムロック (RSW パズル) は「最低計算時間」しか保証できず日付指定に向かないため採用していない

## 限界・注意点

- **書き込み側は使用量を理論上は計算できる**: 追記する以上、プログラムは次の書き込み位置を知る必要があり、その位置は公開鍵から導出できる鍵で封印されている。つまり「公開鍵 + コンテナ」を両方持ち、自分でコードを書いて復号すれば**使用バイト数だけ**は分かる (中身・ファイル名は秘密鍵なしでは不可能)。CLI にはその機能を持たせないことで「うっかり見る」を防ぐ設計。コンテナだけが流出しても使用量は分からない
- **容量不足エラーの意味**: 「このファイルは入らなかった」ことは分かってしまう (残量が少なくともそのファイルより小さい)
- **SSD での物理消去は保証できない**: ウェアレベリングにより、上書きが物理的に同じ記憶セルへ届く保証はない
- **バックアップ**: Time Machine やクラウド同期で過去版が残ると、追記前後の差分から追記位置が推測されうる。消去もバックアップまでは及ばない
- **コピーは消えない**: `--and-destroy-key` が消すのは開封した端末上のファイルだけ
- **平文の残留**: 元ファイルは `--delete-original` を使わない限り残る。エディタの自動保存やシェル履歴までは面倒を見ない
- **drand への依存**: タイムロック鍵は drand がその日まで存続していることが前提。消えていたら非常口でしか開けられない
- **信頼の前提**: drand 運営団体の過半数が結託すれば早期に開けられる。非常口を持つ人はいつでも開けられる
- 秘密鍵のパスフレーズ保護は未実装。サイドチャネル攻撃やメモリダンプなどは考慮していない
